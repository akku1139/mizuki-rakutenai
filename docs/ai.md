# AI アシスタント

コードは `src/ai/` にあります。

| ファイル | 役割 |
|---|---|
| `mod.ts` | メンションの受け付け、コマンド処理、会話の管理、返信の送信 |
| `prompt.ts` | システムプロンプト (瑞稀のキャラクター設定) |
| `context.ts` | チャンネルの直近メッセージをモデルに渡すテキストに整形 |
| `embeds.ts` | embed・添付ファイル・転送されたメッセージをテキストにし、embed の画像の URL を集める |
| `types.ts` | プロバイダ共通のインターフェース (`ChatSession`、`AIEvent`) |
| `agent.ts` | エージェントループの共通部分 (Discord の応答とバックグラウンドジョブで共用) |
| `openai.ts` | OpenAI 互換 API のアダプタ (ツール呼び出しのループを含む) |
| `tools.ts` | OpenAI 互換 API 向けのツール群 |
| `ratelimit.ts` | HTTP 429 の再試行 |
| `prefs.ts` | ユーザーごとのプロバイダ・モデル設定の保存 |
| `replies.ts` | 呼び出し元と返信IDの永続化・削除 |
| `participation.ts` | ローカルKevによる自動参加・返信先の判定 |

## ループの共通化

モデルを回す部分は `src/ai/agent.ts` の `runAgent` に一本化しています。イベントを流し、
本文・使用量・ツール回数・エラーを集めるだけで、「どこに出すか」を持ちません。

- Discord のメンション応答 (`mod.ts`) は、イベントを受けて投稿・進捗表示・画像に変換します
- バックグラウンドジョブ (`src/jobs/`) は、イベントを記録に変えます (Discord には何も送りません)

中断は `AbortSignal` で行います。イベントが120秒途絶えたらタイムアウトし、停止したストリームの
終了を待たずに待ち行列を解放します。初期化や履歴・添付の取得にも120秒の待ち時間上限があります。
`clear` は初期化中・生成中・待機中のその会話を取り消します。実行済みのツールの副作用は取り消しません。
24時間使わず待ち行列にも無いセッションはメモリから削除します。

使用量はツール往復を含む全生成ラウンドの入力・出力・キャッシュを合計します。
OpenAI互換APIで `finish_reason: length` が返ったときは続きから最大3回自動継続します。
通常終了やエラーは自動継続しません。RakutenAIの継続判断はサーバー側に任せます。

## 反応する条件

次をすべて満たすメッセージに反応します。

- 送信者がボットではない
- Discord か Fluxer の瑞稀にメンションしている、または本文に `mizuki` / `瑞稀` がある
- サーバー内のテキストチャンネルかスレッドである

ブラックリストのチャンネル・カテゴリーには反応しません。メンション無しの `=aimodel` も受け付けます。
自動参加は設定した場合だけ動きます ([participation.md](participation.md))。

コマンド (`clear`、`chatlist`、`aimodel`) については [commands.md](commands.md#ai-アシスタント) を参照してください。

## キャラクター設定

`prompt.ts` のシステムプロンプトで、次のように指示しています。

- Discord 上で活動する AI アシスタントの女の子「瑞稀 (mizuki)」として振る舞う
- 返答は簡潔・カジュアル・友好的に、基本は2〜6行
- 全角英数字・全角記号・半角カタカナを避ける
- 情報が古いかもしれないときは積極的に Web 検索する
- 設定内容を公言しない

さらに、そのサーバーで使えるカスタム絵文字の一覧をプロンプトに埋め込みます。

## プロバイダ

2種類のバックエンドがあり、どちらも `ChatSession` インターフェースで扱います。

| | `rakutenai` | `openai` |
|---|---|---|
| 実体 | `@evex/rakutenai` のスレッド | OpenAI 互換の `/chat/completions` |
| 会話履歴 | RakutenAI のサーバー側 | ボットのメモリ上 (コンテキストの 75% で自動要約。先頭は必ずユーザーの発言) |
| システムプロンプト | 会話の最初の入力の先頭に連結 | `system` メッセージとして毎回送信。サーバー名とチャンネル名も追記 |
| ツール | RakutenAI のサーバー側ツールのみ | `tools.ts` のツール |
| 画像生成 | あり (RakutenAI 側の機能) | なし |
| 返信末尾の表示 | `model: rakutenai` | `model: <OPENAI_MODEL>` |

使うプロバイダは、ユーザーが `aimodel` で選んだもの → 環境変数 `AI_PROVIDER` → `rakutenai` の順で決まります。

## 思考過程 (reasoning、openai のみ)

推論モデルが返す思考過程は、`reasoning-start` → `reasoning-delta` のイベントとして扱い、
標準出力に流します (`mod.ts` のログ)。返信本文には混ぜませんが、一部のプロバイダ (DeepSeek 系など) は
過去の assistant メッセージの思考過程 (`reasoning_content` / `reasoning`) の再送を要求するため、
会話履歴の assistant メッセージには思考過程を保持して再送します。

- 思考過程があったターンは、そのまま再送します
- **ツール呼び出しを含む assistant メッセージには、思考過程を返すモデルなら必ず付けます**
  (空でも)。直前の思考を要求するプロバイダがあるためです。モデルが返したツール呼び出しの
  理由づけもここに残ります
- 思考過程を一度も返さないモデルには付けません (そのフィールドを知らないプロバイダでは
  未知の引数として 400 になるため)

OpenAI 公式のスキーマには無いフィールドなので、互換サーバーが使う次の2つの名前を両方読みます。

| フィールド | 返すサーバーの例 |
|---|---|
| `reasoning_content` | DeepSeek、vLLM、SGLang、GLM |
| `reasoning` | OpenRouter |

どちらも無ければ、これまでどおり本文 (`content`) だけを扱います。

## 会話の単位と順番

- 会話は「チャンネル × ユーザー」ごとに1つです。同じチャンネルでも、ユーザーが違えば別の会話になります。
- 同期している Fluxer チャンネルは、同期先の Discord チャンネルの ID で扱います。
  そのため、Discord と Fluxer のどちらから話しかけても同じ会話が続きます。
- 同じ会話への依頼は1件ずつ順番に処理します (Promise チェーン)。別の会話は並行して処理されます。
- セッションの初期化も待ち行列の内側で行い、初回の同時呼び出しから順番を保証します。
- エラー・中断の後は次の依頼で新しいセッションを作ります。別ユーザーの処理は止めません。
- `ai.sharePublicChannelContext: true` を設定すると、同一サービス・同一サーバー内の全員が読める
  テキストチャンネルで、本人の履歴を共有します (既定 false)。別ユーザー・別サーバー・非公開・
  NSFW・スレッドとは混ぜません。共有元が非公開化された場合は次の依頼で共有履歴をリセットします。
- `aimodel` によるプロバイダ・モデルの変更は本人の全チャンネルのセッションをリセットします。

## モデルに渡す文脈

毎回の入力は `context.ts` で次のように組み立てます。

1. `[System] あなたの前回のメッセージID: ...` (前回の返信がある場合)
2. 返信先のメッセージ (返信でメンションした場合)。返信先の前後10件のうち、返信先と同じ人の投稿を古い順に並べる。
   直近の欄からは重複を除き、前回の自分の返信より古くても載せる。瑞稀自身への返信では付けない
3. 直近のメッセージ (最大100件)。前回の自分の返信より後のものだけを、古い順に並べる
4. 今回メンションされたメッセージ

各行は `[メッセージID] (reply to ...) 時刻 | 表示名 (ユーザー名, ID): 本文` の形式です。
同じ人の連続投稿は名前を省略し、ボットの発言には `[BOT]` を付けます。

本文には、次のものもテキストにして続けます。

- embed: `[embed: サイト名 / 作者 / タイトル / 説明 / フィールド / フッター / (画像)]` の形で1行にまとめます。
  説明は300文字、embed 全体は600文字で切ります。リンクのプレビューの URL は本文にあるので省き、ボットの embed の URL だけ付けます。
- 添付ファイル: `[添付: ファイル名]`
- 転送されたメッセージ: `(forwarded)` に続けて、転送元の本文・embed・添付ファイル
全体は最大10,000文字です (RakutenAIではシステムプロンプトを含む)。今回の依頼と返信先を優先し、
残りに最新側から入る分を選んで、古い順に並べます。過去の発言と今回の依頼の間に `after` は指定しません。
今回の依頼自体が上限を超えても依頼を切り捨てません。

OpenAI互換APIでは、ツールの結果を全て履歴に積んでから次の生成前にチャンネルの新着100件を確認し、
まだ渡していない発言を1回ずつ注入します。自分の途中出力は除き、他の並列応答・人間の新着発言・添付を
取り込みます。これにより履歴の `assistant(tool_calls)` と `tool` の対応を壊さず、途中の指示も反映できます。

## 添付ファイル

今回のメッセージ、返信先、直近の履歴の添付・embed画像を渡します。転送されたスナップショットも
対象です。今回の添付・返信先を優先し、それ以外は新しいものから選びます。

- embedの画像と画像・GIF・動画プレビューのサムネイルが対象 (記事の小さいサムネイルは除く)
- Discord / Fluxer のプロキシURLから取得し、1通のembed画像は最大4枚、1ターンのファイルは合計20件まで
- 同じURLは重複して送らず、取得失敗はログに残して飛ばす。各ダウンロードの上限は30秒
- OpenAI互換APIでは `fetch_message` / `fetch_messages_history` で読んだ過去メッセージの添付も、
  ツール結果の後で画像・テキストとして次の生成へ渡す (URLの文字列だけにしない)
- 新着発言を取り込む際も同じ上限内で添付を渡す
- プレビューがまだ作られていない時点では画像を取れない

- `rakutenai`: RakutenAI にアップロードします
- `openai`: base64 の data URL にして送ります
  - 画像は `image_url` として渡します
  - テキスト系 (`text/*`、JSON、XML、YAML、CSV) は本文を展開します (最大20,000文字)
  - それ以外は「読み取れない形式」と伝えます

## 返信の送り方

- 見出しの `####` 以下は `###` に揃えます
- **Discord のメッセージリンクは `[(1)](<url>)` に置き換えます** (初出順の番号、同じ URL は同じ番号、
  コード内はそのまま)。sakana と同じ出典の出し方で、本文に長い URL が並ばないようにします
- リンクのプレビュー (embed) を出さないよう、URL を `<...>` で囲みます
  (`https://github.com/` → `<https://github.com/>`、`[GitHub](https://github.com/)` → `[GitHub](<https://github.com/>)`)。
  コードブロックとインラインコードの中は触りません (`src/utils.ts` の `suppressEmbeds`)
- 1500 文字ごとに分割しますが、**コードブロックは壊しません**。収まるコードはそのまま 1 通、
  収まらないコードは ` ```lang ` を付け直して分割します (シンタックスハイライトは保たれます)
- botの通常投稿・返信には `allowedMentions: { parse: [], repliedUser: false }` を設定し、本文のメンションで通知しません
- URL内の括弧はそのまま残し、Markdownの外側の括弧だけをURLから除きます
- 末尾に `-# model: <ラベル> (ツール名: 回数, ...)` を付けます
- ツールを呼び出すたびに `-# <説明> (<ツール名>)...` と進捗を投稿します
- RakutenAI が画像を生成した場合は、サムネイルの URL を投稿してから最終版の URL に編集します

呼び出し元が削除されたら、分割した本文・画像・ツール進捗を削除し、生成中なら中断します。
一括削除にも対応し、対応表は `data/ai_replies.json` に保存して再起動後の削除イベントにも使います。
権限不足等で削除できなかった対応は残し、エラーをログに記録します。bot停止中に発生し、再接続時にも
配信されなかった削除イベントは検出できません。

## 記憶 (memory、openai のみ)

ChatGPT の memory と同じ方式です。**保存した事実の抜粋を、待ち行列で自分の順番が来てから毎ターン読み直して注入します。検索はしません。**

- 保存単位は「1 行 1 事実」。会話ログではなく、人物の性格・立場・好み・関係、プロジェクトや決定、用語を持つ
- 保存先はサーバーごとの `data/memory/<guildId>.json` (1 サーバー 1 ファイル。他のサーバーとは混ざらない)
- 毎ターン、依頼文 (と返信先) の前に「覚えていること」として最大 1,200 文字を差し込む
- 優先順は **ピン留め > 話している本人の事実 > 依頼文に出てきた語に当たった事実 > サーバーの最近の事実**。
  入りきらない分は落とす (件数ではなく文字数で切る)

モデルは `memory` ツールで書き込む (システムプロンプトで記録を促している)。

| action | 内容 |
|---|---|
| `remember` | 事実を保存する。`scope: user` (既定、話し相手について) / `scope: guild` (サーバー全体)。`tags` は想起に使う名前・別名。根拠としてメッセージ URL を自動で残す |
| `forget` | id か本文の一部で消す |
| `search` | 語で探す (古い事実を確認したいとき) |

同じ事実 (空白・句読点の揺れを無視して一致) は増やさず、内容と時刻を更新します。
1 サーバー 500 件を超えたら、ピン留め以外の古いものから捨てます。

記録の方針 (プロンプトに入っている指示):

- 記録する: 人物の性格・立場・好み・関係、プロジェクト、決定、用語の由来
- 記録しない: 挨拶・相槌・その場限りの雑談・推測・機微情報 (連絡先、本名、住所)
- 1 回 1 事実、現在形で短く。「〜と言った」の形にしない

### Notion との関係 (2 段構え)

Notion は禁止しません。**インラインに載せられる量には限りがある**ので、2 段に分けます。

| 段 | 置き場 | 役割 |
|---|---|---|
| 索引 | `memory` ツール → `data/memory/<guildId>.json` | 短い事実。毎ターン自動でプロンプトに載る (抜粋、1,200 文字まで) |
| 記録 | **Notion (MCP ツール)** | 人物ページ・経緯・一覧・引用など長い記録。モデルが Notion のツールで検索・読み出し・追記する |

システムプロンプトでは、**返答を書く前に**次を保存するよう指示しています (会話が流れると残らないため)。

- 新しく知った事実・決定・用語の由来・人物の立場や関係
- 面白いネタ・名言・迷言・レスバの構図・食い違い
- 調べ物の結果 (根拠リンク付き)

保存先は「1 行の索引は `memory`、詳しい内容は Notion のページ」です。

- プロンプトの「覚えていること」の見出しには **全何件のうち何件を載せているか** を書きます。
  抜粋に無い話は `memory` の `search`、それでも足りなければ Notion を見る、とモデルに伝えます
- 記録の置き場・道具の名前・URL・仕組みは**会話に出さない**よう指示しています
  (見つけたことは内容だけを話し、根拠は元のメッセージリンクで示す)

#### 公開 (Notion Sites) は指示していません

この環境の Notion MCP には公開系のツールがありません (`notion-get-tool-access` で確認:
`create_pages` / `update_page` / `search` / `fetch` / `move_pages` などは available、
publish / site / share の類は無し)。Notion API の `public_url` も**読み取り専用**です。
そのため「記事を公開する」指示は出さず、ページを作って記録するところまでにしています。

### プロンプトキャッシュのための設計

システムプロンプトはセッションを作るときに 1 回だけ組み立て、**ターンごとに変えません**。
記憶の抜粋は**ユーザーメッセージの先頭**に差し込むので、prefix cache は壊れません
(変わるのはユーザーターン以降だけ)。

`memory` ツールは次の操作を持ちます。

| action | 内容 |
|---|---|
| `remember` | 保存。`facts: [{ text, scope?, tags? }]` でまとめて保存できる (1 回 20 件まで) |
| `forget` | id か本文の一部で削除 |
| `search` / `recall` | 語で探す (全件から。プロンプトの抜粋に無いものも引ける) |
| `stats` | 件数 (全体・ユーザー別・ピン留め) |

記憶は**サーバー単位**です (`data/memory/<guildId>.json`)。Notion 側は MCP なので
ワークスペース全体で共有されますが、bot が書く内容はそのサーバーの会話から作ります。

### Wikiとこれから (sakana 式の「木」)

保存済みの事実は [記憶Wiki](memory-site.md) で記事・出典・月別年表・検索として表示できます。
公開範囲はサーバーごとに選びます。Wikiは既存のJSONを読むだけで、新しいローカルDBは作りません。

出来事 (episodes) とページ (pages) の木、根の常駐、`memory` ツールでの `path` / `episode` 探索は
[sakana](https://github.com/tako0614/sakana) の設計をそのまま使えますが、**ローカルに DB は作りません**。
pages はサーバーごとの Notion データベースに置き、bot は起動時に軽量な索引 (id・名前・別名・タグ) だけを
メモリに持って想起する形にします。埋め込み (意味検索) は v1 では使いません — 名前・別名の照合と
単語の一致で足りる範囲から始め、必要になったら API (`text-embedding-3-small` は $0.02/100万トークン) で
足せるようにします。

## 会話履歴の auto-compact

履歴は件数ではなく**トークン数**で管理します。コンテキストウィンドウの 75% を使ったら
(`src/ai/compact.ts`、teapot の compact の移植)、毎リクエストの前に次のように圧縮します。

1. **古いツール出力を削る** — 直近 (予算と同じだけのトークン) より前の `tool` メッセージのうち、
   3,000 文字を超えるものを頭 400 文字 + `…[pruned N bytes of <ツール名> output]` に置き換える。
   対象は出力が長いだけのツール (`fetch_message`、`fetch_messages_history`、`search_messages`、
   `wikipedia_*`、`read_web`、`search_web`、`run_tool`、`mcp__*`)。これだけで予算に収まれば
   要約は呼ばない (要約よりずっと安い)
2. **要約** — 直近 15,000 トークン (予算の 1/4 が上限) をそのまま残す位置を後ろから探し、
   それより前を AI に 1 回で要約させて 1 通に置き換える (履歴の先頭は `user` メッセージのまま)
3. 要約のリクエストには system プロンプトと古い履歴だけを渡す (ツールは渡さない)
4. 2 回目以降の compact は、前回の要約を渡して「更新」させる (解決したことだけ消す)

- 要約に失敗したら (連続 3 回で要約自体を諦めたら)、**古い方を破棄してでも予算に収めます**
  (`…破棄されました`)。縮めずに放置すると、ツールを叩き続けたターンでウィンドウを超えて
  400 になり、セッションごと捨てられるため (実測: 1M のモデルに 1,885,392 トークンを送って 400)。
- 残す側だけで予算を使い切っているときは要約を呼ばず、削る/捨てるだけにします。
- 切れ目は必ずツール呼び出しとその結果の間を避けます (`assistant` の `tool_calls` と
  対応する `tool` が別側に落ちると 400 になるため)。
- 予算で使うトークン数は、API が返した入力トークン数 (`usage.prompt_tokens`) があれば
  それを使い、無ければメッセージから推定します (英語 4 文字 / トークン、日本語 1.2 トークン / 文字)。
- ツールを大量に呼ぶターンは 1 回で窓を食い潰すので、判断はターンの開始時ではなく
  **リクエストのたび**に行います。

コンテキストウィンドウは次の順で決めます (`src/ai/model-meta.ts`、teapot の移植)。

1. 設定 `ai.contextWindowTokens` / `ai.openaiProfiles.<名前>.contextWindowTokens`
2. **モデルカタログ** — プロバイダの `GET /models` の `context_length`、無ければ
   [models.dev](https://models.dev) の `limit.context`
3. どちらも分からなければ 128,000 トークン

カタログは `baseUrl` のホストで引きます (models.dev の 233 プロバイダを API ホストで照合し、
同じホストを複数のカタログに分けているプロバイダはパスで選び分けます)。一覧はプロバイダが正で、
models.dev は穴埋めです (`reflection/beam:free` のように models.dev に載っていないモデルがあり、
逆にプロバイダが能力を公開しないこともあるため)。取得は 1 時間 (失敗は 5 分) キャッシュし、
セッションをまたいで使い回します。決まった値は起動後の最初のリクエストでログに出ます。

```json
{ "ai": { "contextWindowTokens": 1000000 } }
```

設定を書くとカタログより優先されます。**設定を間違えて実際より大きくすると、compact が走る前に
API が 400 を返してそのセッションは捨てられます** (小さい分には早めに要約されるだけで害はありません)。

## ツール (openai のみ)

`tools.ts` は akku1139/evex-quotes の `src/aitools` を移植したものです。
各ツールには `$explain` (何をするかの説明) という引数が自動で追加され、進捗表示に使われます。

| ツール | 内容 | 有効になる条件 |
|---|---|---|
| `fetch_message` | Discord / Fluxer のメッセージ URL から1件取得 | 常に |
| `fetch_messages_history` | メッセージ URL かチャンネルメンションを起点に、前後の履歴を取得 (既定30件、最大100件、`after` / `before` / `around`)。`channel` は URL / `<#id>` / ID / `#名前` / 名前 (曖昧一致) のどれでもよい | 常に |
| `search_messages` | サーバー内のメッセージ検索。Discord の検索構文を受け付ける (下記) | 常に |
| `wikipedia_search` | 日本語版 Wikipedia を検索 | 常に |
| `wikipedia_read` | 日本語版 Wikipedia の記事本文を取得 | 常に |
| `read_web` | `GET ${READABILITY_ENDPOINT}?url=<URL>` で Web ページを読む | `READABILITY_ENDPOINT` を設定 |
| `search_web` | `GET ${SEARCH_ENDPOINT}?q=<クエリ>` で Web 検索（クエリを配列で渡すと並列検索） | `SEARCH_ENDPOINT` を設定 |

`read_web` と `search_web` は、エンドポイントが返した JSON をそのままモデルに渡します。`search_web` にクエリを配列で渡すと、すべてのクエリを並列で実行し、結果を配列で返します（1 クエリのときは単一結果）。

ツールの実行とモデルの再生成に回数上限は設けていません。モデルがツール呼び出しを返し続ける限りループします。
1回の API リクエストのタイムアウトは120秒です。

## MCP ツール

`data/config.json` の `mcpServers` でつないだ MCP サーバーのツールを、モデルから使えるようにします
(`src/ai/mcp.ts` / `src/ai/mcp-registry.ts`)。実装は teapot のクライアントの移植です。

- ツールが 20 個以下なら、そのまま `mcp__<サーバー名>__<ツール名>` として並べます
- それを超えると、`search_tools` (キーワード検索) と `run_tool` (tool_id を指定して実行) の 2 つに畳みます。
  `search_tools` は既定で引数のスキーマを返しません (トークンを使うため)。必要なら `include_schema: true`
- ツール定義は**リクエストのたびに引き直します** (`ToolSpec.definitions` は関数でもよい)。
  MCP サーバーは再接続でツールが増減するので、セッション生成時の一覧を固定すると、
  接続が切れた瞬間に作られたセッションが以後ずっと MCP ツール無しになります
  (エラーでセッションが作り直された直後がこれに当たりました)
- ツールの結果は **text だけではありません**。`resource` (埋め込みリソース)・`resource_link`・
  `image`・`audio`・`structuredContent` をすべてテキストにします。`resource` が `text` を持たず
  `uri` だけなら `resources/read` で取りに行きます。ここを text だけにすると、GitHub MCP の
  `get_file_contents` のようなサーバーが返す**ファイルの中身がまるごと捨てられ**、
  モデルには `[resource content omitted]` しか届きません
- 失敗したツールは `ok=false` として、エラー本文を `{ error }` で返します

## メッセージ検索 (`search_messages`)

Discord の検索 API (`GET /guilds/{id}/messages/search`) だけを使います。bot でも使えますが、
`READ_MESSAGE_HISTORY` 権限と `MESSAGE_CONTENT` privileged intent が要ります。
索引がまだ無いサーバーでは `202` と `retry_after` が返るので、少し待って 1 回だけやり直します。

**ローカルで絞り直すことはしません** (API の判定をそのまま信じます)。
検索語も条件も無いクエリ (`query` 未指定・空文字・`in:` だけ) は、API が返す「そのチャンネルの最新」を
検索結果として返してしまうため**エラーにします** (直近を読みたいときは `fetch_messages_history`)。
`channels` を省略したときは現在のチャンネルだけを検索し、そのことを結果の `scope` に書きます。API が失敗したら、
理由と確認事項を添えてエラーを返します。チャンネルを遡るフォールバックは持ちません
(最新しか見ていないのに「全チャンネルを読んだ」と誤解させるため)。

検索語は Discord の書き方 + 少し足したものです。**API が解釈するものだけ**を渡します。

| 書き方 | 内容 | API |
|---|---|---|
| `語` | すべて含む (AND) | `content` |
| `"フレーズ"` | 空白込みの一致 | `content` |
| `-語` | 含まない | `content` (`-語`) |
| `語 OR 語` | どちらか | **API 非対応** → 語ごとに 1 回ずつ検索してまとめる |
| `from:名前/ID` | 投稿者。名前はメンバーから解決 (キャッシュ → 問い合わせ) | `author_id` |
| `in:#チャンネル` / `in:ID` / `in:URL` | 対象チャンネル (`channels: "all"` でサーバー全体・最大12) | `channel_id` |
| `mentions:ユーザーID` | メンション先 | `mentions` |
| `has:image` `has:file` `has:link` `has:embed` `has:sticker` `has:poll` `has:video` `has:sound` | 添付・埋め込みの種類 | `has` |
| `before:` `after:` `during:` `on:` | 期間 (絶対・相対 `7d` など) | `max_id` / `min_id` |
| `is:pinned` | ピン留め | `pinned` |
| `sort:old` | 古い順 | `sort_order` |
| `regex:/…/i` `len:>100` | — | **API 非対応**。`unsupportedOperators` として返す (これだけのクエリはエラー) |

日本語の長い文 (`techfishの不祥事について教えて`) は、助詞・依頼表現で割ってから `content` に渡します
(そのまま渡すと API は 0 件を返します)。

結果には `channels: [{ id, name }]` を返すので、続けて `fetch_messages_history` を呼ぶときにそのまま
ID を渡せます。見つからないチャンネルは `近い候補: #…` を返します。

**2 ページ目以降**も読めます。結果の `total` が総ヒット数、`nextOffset` が続きの位置です
(`limit` は最大 100、API へは 25 件ずつ問い合わせます)。

```json
{ "query": "techfish", "limit": 25, "offset": 25 }
→ { "total": 141, "offset": 25, "nextOffset": 50, ... }
```

`offset` は Discord の検索結果に対する生の位置です。`OR` と併用したときは、語ごとに検索して
まとめる都合で件数がずれることがあります。

## 失敗したときの再試行 (openai のみ)

`src/ai/ratelimit.ts` の `fetchWithRetry` に一本化しています。SDK 側の再試行は
`maxRetries: 0` で止めてあり、二重に再送しません。

| 種類 | 扱い |
|---|---|
| 429 | 再試行。`Retry-After` (秒数 / HTTP 日時) に従い、無ければ 1・2・4 秒 + 最大1秒のジッタ。60秒を超える要求は諦める |
| 5xx / 408 / 425 / 接続断 | 上流が一時的に落ちていることがあるので再試行。待ちは短め (250ms・500ms・1s + ジッタ) |
| 400 (「could not be rendered into a prompt」) | **1回だけ**再試行。ゲートウェイのルーティング先が変わると同じ本文で通ることがある |
| その他の 400 / 401 / 403 / 404 | 何度送っても同じなので再試行しない |
| 残高不足・クォータ (`insufficient_quota` など) | 待っても解決しないので再試行しない |
| ストリーミング開始後の切断 | 再試行しない (実行済みのツールをやり直さない) |

再試行の上限は 3 回 (初回を含めて最大 4 リクエスト) です。

### 400 を減らすための正規化

送信前に `#sanitize` でメッセージを均しています。

- `content: null` の assistant は **content ごと省く**(ツール呼び出しのときだけ null を許さない
  プロバイダがあり、400 "could not be rendered into a prompt" になる)
- 中身もツール呼び出しも無い assistant は捨てる
- 対応する assistant が無い `tool` メッセージは捨てる

400 が返ったときは、送ったメッセージの形 (`role/文字数/calls`) をログに残します。
